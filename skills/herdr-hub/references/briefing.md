# briefing（worker へ渡す雛形）

worker が受け取る唯一の作法書は briefing である。worker はこの skill を読まない前提で、**動くのに必要な全てをここに書く**。

## 7 ブロック

この順で書く:

1. **宛先 guard** — 「このメッセージは agent `<name>` 宛です。あなたの名前が違うなら着手せず hub へ返信してください」
2. **役割と一元化** — あなたの roster 上の役割 / 指示は hub からのみ / 人間への直接の質問はしない。roster に `role_def` が指定されている agent には、hub がそのファイル内容を役割ブロックへそのまま注入する
   - **担当の「外側」を書く。** 何が含まれず、どこへ送られるか（別の担当・別の成果物）。送り先が書かれていない分割は、後から「落ちた」のか「送った」のか区別できない
3. **最初の一手** — 何を・どこから始めるか。**着手前に一度止まる、を既定にする。** 資料を指すときは節名で指す（行番号ポインタは腐る）。file を渡すときは `latest` のような共有可変ポインタでなく**絶対パス**で渡す
4. **その担当が最初に踏む既知の罠** — 前任の失敗・申し送りをここへ集約。**必ず埋める**（最も効くブロック。空なら同じ穴を 2 度踏む）。1 件ずつ「何が起きるか → なぜ検出できないか → どうするか」で書く。**誰も確認していない箇所は「確認していない」と明示する**
5. **作法** — 下記「worker の作法」
6. **境界** — やってよいこと・止まる条件（許可が要る操作、スコープ外）。roster の `rules`（defaults・preset・個別を union したもの）があれば、**各 file の本文を改変せず全文をここへ注入し、出所パスを併記する**（要約・抜粋・言い換えをしない — 「file を編集すれば worker に届く」が rules の約束であり、黙って削ると削った側にも受け手にも分からない。role に無関係な行も残す）
7. **進め方** — 報告の粒度・区切り・終了条件。**一気に進めさせない**（区切りごとに報告）。担当の大きさを数字で伝える

## worker の作法（⑤ に含めるもの）

- **あなたの名前は `<name>`。** 返信・報告は `herdr agent prompt hub "..."`（または Claude なら SendMessage で `hub` 宛）で **hub へ**
- roster 上の他 agent の名前と役割（誰に何を直送してよいかの判断材料）
- **進捗・判断・罠は `/tmp/herdr-hub/<name>.log` へ随時追記する**（交代時の handoff はこれへの参照になる → [context-and-handover.md](context-and-handover.md)）
- **他 agent を `herdr agent wait` 等で監視しない。** 待つべきものがあるときは「何を待っているか」を 1 行で hub へ投げてターンを終える
- **新しい作業（issue・別タスク化）を自分で発行しない。** 「候補」として hub へ上げる
- **承認 UI で止まったときはそのまま待つ** — hub 側には `agent_blocked` として見える
- 判断・裁定が必要に見えたら hub へ上げる。自分の権限を越える決定をしない
- **hub へ問い合わせるときの作法**（宛先の名指し・「決断が要る」の標識・裁定の着手確認・待ち方）は [messaging.md](messaging.md)「逆方向」の項目を briefing に含める

### 報告の作法

- 報告の形は **① 結論 → ② 次のアクション → ③ 理由・裏取り**
- **数値は実行出力の逐語のみ。** 推測を書かない。報告に数値が 1 つでも入るなら、本文を書く前に全部測る — 「編集の結果」を主張する文も、編集後にその場で照会して出力を貼る
- **観測と解釈を分けて報告する**
- **`file:line` を書くときは ref（branch・commit）を明示する。** 同時刻でも branch が違えば行番号が違う
- **hub が渡した数値・区分・列挙はすべて未検証の入力として扱い、取り直してよい**（むしろそうする）
- **状態の数値を報告の主題にしない。** CI の緑/赤・失敗件数・進捗・使用率は**状態**であり、作者と CI が既に観測している。重複は情報を増やさない。**判定（主張の真偽）は独立に取り直す**
- 🔴 **context 使用率を「報告のたびに添える」欄を作らない。** 「毎回添えろ」という欄は、埋めることが目的化し、測らずに埋める圧力になる（捏造の実害あり）。**停止条件は hub が条件として持ち、申告はさせない** — 必要なときに hub が名指しで訊く
- **hub が名指しした箇所の数は下限である。**「N 箇所を直せ」は hub が見つけた数でしかない。**決定単位で全数走査して、名指しされていない箇所を含めて直す。** 指示外を直したときは報告でその旨を明示する（review 対象に含める必要があるため）

## 「裁定」の明記

hub が自分の推奨を worker へ送るときは **「これは私の裁定であり人間の決定ではない」と本文に明記する**。書かないと受け手には hub の推奨と人間の決定が同じ形で届く。逆に人間の決定を転送するときは**決定文を逐語で添える** — 「承認済みの認識です」は転送ではない。

## review 担当への差分

review を担う worker には、最終ブロック（進め方）の前に以下を追加する:

- **対象を SHA で固定する。** branch 名だけを渡すと、対象が進んだ分だけ stale な指摘を量産する。`head : <SHA>`（ただし着手時に取り直す）と `base : <SHA>` を渡し、**review した SHA を報告に書かせる**
- **既に照会済みの範囲を書く**（再指摘を減らす）。「あなたが最初の目です」なら、そう書く
- **1 人目の reviewer が走行中に 2 人目を振るときは、先に 1 人目の「読んでいない file」を確認してから割る。**「別軸」を指定しても重複した実害あり — 軸の宣言ではなく未読範囲の実測で分ける
- **「非同期に走っている補助作業（追送・追加の確認）はあるか」を報告に必ず書かせる。** 書かれていないと、hub は「これで全部」と読んで worker へ流し、後から届いた追送で同じ対象をもう一度直させる形になる
- **hub が下した裁定は、そう明示して「遠慮なく壊してください」と招く。** hub は自分の裁定の周辺で検査が効かない（[adjudication.md](adjudication.md)）。独立性が落ちる軸（材料が自分で渡したもの等）は先に申告させる
- **挙げた観点に狭く当てさせない。**「それ以外に見つけたものも出してください」を必ず書く。**「私の主張を出発点にしないでください。全文を先に読んでから突き合わせてください」** — 主張から出発すると、主張の外にあるものは構造的に見つからない
- **定常観点に「実装の作用範囲（対象集合・段）が正典の定義と一致するか」を含める。** 実害: spec の段表が限定していた範囲を実装が広げた欠陥を、hub 裁定・review・突合のいずれも拾えなかった — 「導出元と一致するか」だけでは「導出元が正典の集合か」は測れない
- **期待値の事前登録**: review が修正前の baseline を実測してから修正を依頼する。「after が変化した」で効果を張れる。「test が増えた」では足りない
- **複数巡になる review で、巡の所見を実装側へ渡すときは「直し方の方向」の各項も処置対象と明記する。** 指摘本体だけが処置されて方向の一部が残り、次巡で再掲になった実害あり
- **完了・merge の通知が来たら、その対象への review 活動を止める**（並行起動した追走もすべて）。走行中の側は完了を観測できないので、止まるのは通知が届いたときだけ。例外は「既に取り込まれた変更が壊す欠陥」を見つけたときだけ
- **ファイルを編集しない**（報告まで）。push しない・PR を作らない・merge しない

## 交代時・途中参加の分担

交代では briefing を 2 人で書く（手順は [context-and-handover.md](context-and-handover.md)）:

| 書き手 | ブロック |
|---|---|
| **hub** | 宛先 guard / 役割と一元化 / 作法 / 境界 / 進め方（roster 全体の文脈は hub にしかない） |
| **前任** | 現在の状態 / 最初の一手 / 既知の罠（落とした本人が最も詳しく、hub 中継は情報を落とす） |

交代時はブロック 3（最初の一手）の直前に「**現在の状態**」を挿入した 8 ブロック版を使う。**稼働途中に動的追加された agent への briefing も同じ 8 ブロック版** — 「現在の状態」は直近の担当者または hub が書く。

前任が送る内容を hub は検査してよいが、**書き換えて自分の文にしない** — 中継の圧縮で本体が落ちる型になる。
