# briefing（worker へ渡す雛形）

worker が受け取る唯一の作法書は briefing である。skill を読むのは hub だけで、worker はこの skill を読まない前提で、**動くのに必要な全てをここに書く**。briefing は hub が書く。人間に書かせない。

## 渡し方

- briefing は最初の依頼として `hc run` に渡す（`hc-hub spawn-argv … --task`）。長いときは briefing をファイルに書く。長文はファイルに書いてパスを送る（サイズやバーストの超過で拒否されうる）。`--task` には、そのファイルの絶対パスと hub のアドレスを書き、同じパスを `--brief` でラベル（`hc-hub.brief`）に残す
- **command で起こした worker には、`<hc from=… reach=…>` のタグも `first_message` も付かない（実測）。** 報告の宛先（`hc send <hub のアドレス> …`）はタグから得られないので、**briefing に hub のアドレスを自分で必ず書く。** 書き忘れると worker は報告の宛先を持たない
- 届いたかは `hc get` の状態が `working` になる・ターンが進むことで確認する（[startup.md](startup.md)）
- 手での hub の交代では、後任が引き継いだ worker の全員に、自分のアドレスを新しい返信先として `hc send` で知らせる。briefing に書かれた hub のアドレスは前任のままのため

## 7 ブロック

7 ブロックをこの順で書く:

1. **宛先 guard** — 「このメッセージは worker `<名前>`（アドレス `<t>`）宛です。あなたの名前が違うなら着手せず hub へ返信してください」。宛先はヘッダではなく名前とアドレスで示す
2. **役割と一元化** — あなたの roster 上の役割 / 指示は hub からのみ / 人間への直接の質問はしない。roster に `role_def` が指定されている agent には、hub がそのファイル内容を役割ブロックへそのまま注入する（`hc-hub resolve --lane <L> --preset <P>` の `role_def`）
   - **担当の「外側」を書く。** 何が含まれず、どこへ送られるか（別の担当・別の成果物）。送り先が書かれていない分割は、後から「落ちた」のか「送った」のか区別できない
3. **最初の一手** — 何を・どこから始めるか。**着手前に一度止まる、を既定にする。** 資料を指すときは節名で指す（行番号ポインタは腐る）。file を渡すときは `latest` のような共有可変ポインタでなく**絶対パス**で渡す
4. **その担当が最初に踏む既知の罠** — 前任の失敗・申し送りをここへ集約。**必ず埋める**（最も効くブロック。空なら同じ穴を 2 度踏む）。1 件ずつ「何が起きるか → なぜ検出できないか → どうするか」で書く。**誰も確認していない箇所は「確認していない」と明示する**
5. **作法** — 下記「worker の作法」
6. **境界** — やってよいこと・止まる条件（許可が要る操作、範囲外）。roster の `rules`（defaults・レーン・preset・個別を union したもの。`hc-hub resolve` の `rules`）があれば、**各 file の本文を改変せず全文を注入し、出所パスを併記する**（要約・抜粋・言い換えをしない。「file を編集すれば worker に届く」が rules の約束であり、黙って削ると削った側にも受け手にも分からない。role に無関係な行も残す）
7. **進め方** — 報告の粒度・区切り・終了条件。**一気に進めさせない**（区切りごとに報告）。担当の大きさを数字で伝える

## worker の作法（⑤ に含めるもの）

作法ブロックに含めるものを列挙する。

- **あなたの名前は `<name>`。** 返信・報告は `hc send <hub のアドレス> "…"` で **hub へ**。返信は hub 宛で、briefing に書かれたアドレスだけを宛先にする
- 同じレーンの他 agent の名前と役割（誰に何を直送してよいかの判断材料）
- **レーンを越えない。** 送ってよいのは、briefing に書かれた hub のアドレスと、hub に指示された相手だけ。他のレーンの worker には、読むことも含めて触れない。この規律は機構的な遮断ではない（ラベルは自己申告で、ガードは自分に課す規律）ので、守るのは worker 自身である。宛先を取る操作の前に `hc-hub guard --op <op> <t>` を打てる環境ならそれを打つ。[lanes.md](lanes.md)
- **勝手にエージェントを起こさない。** worker が自分で `hc run` して子を起こすと、子はラベルを持たず hub のレーンの外に出る。必要なら「候補」として hub に上げる
- **進捗・判断・罠は log file へ随時追記する**（hub が指定するパスに。交代時の handoff はこれへの参照になる → [context-and-handover.md](context-and-handover.md)）
- **他の worker を `hc wait` 等で監視しない。** 待つべきものがあるときは「何を待っているか」を 1 行で hub へ投げてターンを終える
- **新しい作業（issue・別タスク化）を自分で発行しない。** 「候補として hub へ上げる」
- **承認 UI で止まったときはそのまま待つ。** hub 側には `blocked` として見え、hub が [approvals.md](approvals.md) の範囲で答える
- 判断・裁定が必要に見えたら hub へ上げる。自分の権限を越える決定をしない
- **hub へ問い合わせるときの作法**（宛先の名指し・「決断が要る」の標識・裁定の着手確認・待ち方）は下の「逆方向」を briefing に含める。問い合わせの作法は briefing にしか書かれない

### 報告の作法

- 報告の形は **① 結論 → ② 次のアクション → ③ 理由・裏取り**
- **数値は実行出力の逐語のみ。** 推測を書かない。報告に数値が 1 つでも入るなら、本文を書く前に全部測る。「編集の結果」を主張する文も、編集後にその場で照会して出力を貼る
- **観測と解釈を分けて報告する**
- **`file:line` を書くときは ref（branch・commit）を明示する。** 同時刻でも branch が違えば行番号が違う
- **hub が渡した数値・区分・列挙はすべて未検証の入力として扱い、取り直してよい**（むしろそうする）
- **状態の数値を報告の主題にしない。** CI の緑/赤・失敗件数・進捗・使用率は**状態**であり、作者と CI が既に観測している。重複は情報を増やさない。**判定（主張の真偽）は独立に取り直す**
- 🔴 **context 使用率を「報告のたびに添える欄」を作らない。** 毎回添えろという欄は、埋めることが目的化し、測らずに埋める圧力になる（捏造の実害あり）。**停止条件は hub が条件として持ち、申告はさせない。**必要なときに hub が名指しで訊く
- **hub が名指しした箇所の数は下限である。**「N 箇所を直せ」は hub が見つけた数でしかない。**決定単位で全数走査して、名指しされていない箇所を含めて直す。**指示外を直したときは報告でその旨を明示する（review 対象に含める必要があるため）

## 逆方向（worker から問い合わせるとき — briefing に含める作法）

[messaging.md](messaging.md) の送受信の作法に加えて、worker が hub へ送るときの作法。

- **「誰宛か」を本文で名指しする**（本文先頭に `[<name> 宛]`）
- **裁定を求める便は「決断が要る」と標識を付ける。**標識のない便が遅延する形になる
- **裁定が届いたら、着手してよいかまで確認する**（「指示と受け取ってよいか」）
- **待つ間の代替作業を質問しない。**「X 待ちの間 Y をやってよいですか」は X の待ち中に hub を 1 往復占有する。待つものは 1 行で投げてターンを終える
- **hub への送信が失敗したら、その事実を残して報告し、作業を進めずに待つ。** 黙って別経路を試さない（別経路で送ると「届いていない」が後から分かる形になる）。失敗の表示を画面に残して待つ。後任の hub が引き継いだときは、新しいアドレスを `hc send` で送ってくる。それを受けてから返信先を更新する

## 「裁定」の明記

hub が自分の推奨を worker へ送るときは **「これは私の裁定であり人間の決定ではない」と本文に明記する。**書かないと受け手には hub の推奨と人間の決定が同じ形で届く。逆に人間の決定を転送するときは**決定文を逐語で添える。**「承認済みの認識です」は転送ではない。

## review 担当への差分

review を担う worker には、最終ブロック（進め方）の前に以下を追加する（review 担当への差分）:

- **対象を SHA で固定する。** branch 名だけを渡すと、対象が進んだ分だけ stale な指摘を量産する。`head : <SHA>`（ただし着手時に取り直す）と `base : <SHA>` を渡し、**review した SHA を報告に書かせる**
- **既に照会済みの範囲を書く**（再指摘を減らす）。「あなたが最初の目です」なら、そう書く
- **1 人目の reviewer が走行中に 2 人目を振るときは、先に 1 人目の「読んでいない file」を確認してから割る。**「別軸」を指定しても重複した実害あり。軸の宣言ではなく未読範囲の実測で分ける
- **「非同期に走っている補助作業（追送・追加の確認）はあるか」を報告に必ず書かせる。**書かれていないと、hub は「これで全部」と読んで worker へ流し、後から届いた追送で同じ対象をもう一度直させる形になる
- **hub が下した裁定は、そう明示して「遠慮なく壊してください」と招く。**hub は自分の裁定の周辺で検査が効かない（[adjudication.md](adjudication.md)）。独立性が落ちる軸（材料が自分で渡したもの等）は先に申告させる
- **挙げた観点に狭く当てさせない。**「それ以外に見つけたものも出してください」を必ず書く。**「私の主張を出発点にしないでください。全文を先に読んでから突き合わせてください」** — 主張から出発すると、主張の外にあるものは構造的に見つからない
- **定常観点に「実装の作用範囲（対象集合・段）が正典の定義と一致するか」を含める。** 実害: spec の段表が限定していた範囲を実装が広げた欠陥を、hub 裁定・review・突合のいずれも拾えなかった。「導出元と一致するか」だけでは「導出元が正典の集合か」は測れない
- **期待値の事前登録**: review が修正前の baseline を実測してから修正を依頼する。「after が変化した」で効果を張れる。「test が増えた」では足りない
- **複数巡になる review で、巡の所見を実装側へ渡すときは「直し方の方向」の各項も処置対象と明記する。**指摘本体だけが処置されて方向の一部が残り、次巡で再掲になった実害あり
- **完了・merge の通知が来たら、その対象への review 活動を止める**（並行起動した追走もすべて）。走行中の側は完了を観測できないので、止まるのは通知が届いたときだけ。例外は「既に取り込まれた変更が壊す欠陥」を見つけたときだけ
- **ファイルを編集しない**（報告まで）。push しない・PR を作らない・merge しない

### 「測らない」ことを依頼文へ固定文で注入する

「観測を重複させない」（[adjudication.md](adjudication.md)）は hub 側の文書にしかなく、**reviewer に届くのは依頼文だけ**である。書かなければ reviewer は自分でテストを回し、CI の完了を待つ。依頼文・依頼 file に固定文をそのまま入れる:

```markdown
## テストと CI は測らない
- テストの緑/赤と CI の結果は worker と hub が観測している。あなたは再実行しない・CI の完了を待たない・CI の状態を照会しない。時間は読むことに使う。
- worker の実行記録: <log の path>（test の中身と主張の対応は読んで判定してよい。数字の測り直しは不要）
- 例外: 実行しないと真偽が決まらない主張に限り、名指しの test 1 本だけ走らせてよい。その場合は「何を反証しようとしたか」と結果を所見に書く。
```

- **`<log の path>` は path だけを書く。**hub が件数・pass 数を転記しない（測らずに埋める欄になる）。無いなら「無し」と書き、空欄にしない
- ⚠ 免除されるのは「測ること」であって「読むこと」ではない。test が主張を識別できるか（期待値・変異で落ちるか）は reviewer の判定対象のまま

### review thread の一次判断は worker（hub は却下の検算）

- **採用する指摘はそのまま直す**（hub へ上げない）。**却下だけ全数走査の根拠つきで報告**し、hub の検算を経てから閉じる。自分で却下して自分で閉じない。一次判断は worker が持ち、hub は却下の検算をする
- **返信で終わりにせず resolve まで打つ**（「返信する」と「解決する」は別操作）。resolve の前に「何をしたか（修正 commit / 却下の根拠）」を返信で残す。処置の出所が記録から消えない
- **報告には `total N / unresolved M` を母集団ごと添える。**`unresolved: 0` だけでは「解決済み」と「thread が 1 本も無い」を区別できない

## 交代時・途中参加の分担

交代では briefing を 2 人で書く（手順は [context-and-handover.md](context-and-handover.md)）:

| 書き手 | ブロック |
|---|---|
| **hub** | 宛先 guard / 役割と一元化 / 作法 / 境界 / 進め方（レーン全体の文脈は hub にしかない） |
| **前任** | 現在の状態 / 最初の一手 / 既知の罠（落とした本人が最も詳しく、hub 中継は情報を落とす） |

交代時はブロック 3（最初の一手）の直前に「**現在の状態**」を挿入した 8 ブロック版を使う。**稼働途中に動的追加された agent への briefing も同じ 8 ブロック版**で、「現在の状態」は直近の担当者または hub が書く。

前任が送る内容を hub は検査してよいが、**書き換えて自分の文にしない**。中継の圧縮で本体が落ちる型になる。
