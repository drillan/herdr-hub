# hc-hub init — 新しいプロジェクトに roster を用意する機能の設計

2026-10-31。`skills/hc-hub` の同梱 CLI に、新しいプロジェクト向けの roster（`.hc-hub.yml`）を用意する機能を足す。手元の環境で使えるコーディングエージェントを調べ、その中から人が選んだものを roster に書く。

## 1. 意図

hc-hub は roster が無いと明示エラーで止まる（台帳のパス `ledger` が必須のため）。今は、同梱の `.hc-hub.yml.example` を手でコピーし、パスやコマンドを直す前提になっている。

新しいプロジェクトで hc-hub を使い始めるときに、次の 2 つでつまずく。

- **どのエージェントを roster に書けるかが分からない。** 試運転では、シェルからは見える opencode が hc の core からは見えず、`hc run` が `spawn_failed` で失敗した。「インストールされている」と「`hc run` で起動できる」は別物である。
- **雛形を手で直す手間と、直し忘れ。** 雛形のパスは実在を前提にしていない。`.hc-hub/` を git の管理から外す手順も、別に要る。

## 2. 目標・目標外・失敗とみなすもの

**目標**

- hc の core から起動できるエージェントを、`hc run` と同じ環境で調べる
- 調べた結果を、人が選べる形で示す。シェルからは見えるのに core からは見えないものは、その旨と直し方を添えて示す
- 人が選んだ内容だけを roster に書く。書いた roster が `hc-hub validate` を通る

**目標外**

- 選ばれなかった項目を、CLI が既定値で埋めること
- 既存の `.hc-hub.yml` を書き換えること（追記・統合を含む）
- 規律のファイル（`rules`）や役割定義（`role_def`）の中身を作ること
- core の PATH を書き換えること

**失敗とみなすもの（動いても不可）**

- core から起動できないエージェントを、起動できるものとして roster に書く
- 個人の絶対パス（`/home/<ユーザー名>/…`）を roster に書く
- 人が選んでいない approval やエージェントが、roster に入る

## 3. 前提となる実測（2026-10-31）

同じマシンで `which claude codex opencode devin copilot pi` を 3 か所で実行した。

| 実行した場所 | claude | codex | opencode | devin | copilot | pi |
|---|---|---|---|---|---|---|
| hc の端末の中（`hc run -- which …`） | ✓ | ✓ | ✗ | ✓ | ✓ | ✗ |
| ユーザーの対話の zsh（`zsh -ic`） | ✓ | ✓ | ✓（`~/.opencode/bin`） | ✓ | ✓ | ✗ |
| エージェントの Bash ツール（対話でないシェル） | ✓ | ✓ | ✗ | ✓ | ✓ | ✗ |

- `hc run` が起動できるかどうかと一致するのは、hc の端末の中の結果だけである
- `hc run --rm` で起動すると、結果を読む前に端末が消える（実測）
- `which` は、見つからないものがあると終了コード 1 で終わる（実測）

hc の使い捨て端末の扱い（hc 0.1.15 で実測）:

- `hc run --json --bg --no-parent --name <名前> -- sh -c '<スクリプト>'` は `{"address":"t28","agent":"sh",…}` を返す。端末の識別子は `address`
- `hc wait --json <t> --timeout <秒>` は、中のプログラムが 0 以外で終わっても、自身は終了コード 0 で返る。中の終了コードは JSON の `exit_code` に入り（例: `{"ended":true,"exit_code":3,"reason":"exit",…}`）、`reason` は `exit`。`wait` 自体の失敗とは、`wait` の終了コードと `reason` で区別できる
- `hc read <t>` は画面の文字を返す。制御文字は混ざらなかった。**タブは空白に変わる**ので、区切りにタブを使わない
- `/bin/sh` は dash で、**`command -v a b c` は最初の名前しか調べない**（`command -v claude opencode devin` が claude の行だけを出し、終了コード 0 だった）。名前ごとにループで 1 回ずつ呼ぶ
- 名前ごとのループで `<名前> <パス>`（見つからなければ `<名前>` だけ）を 1 行ずつ出す形は、意図どおりに読めた

## 4. 振る舞い

### 4.1 二段に分ける

調べることと書くことを、別のサブコマンドに分ける。そのあいだで、人が選ぶ。

1. `hc-hub detect` — 調べて、結果を JSON で出す（書き込みはしない）
2. hub を務めるエージェントが、結果を人に示す。どのエージェントにどの役割を割り当てるか、approval を `auto` と `manual` のどちらにするかを、人に選んでもらう
3. `hc-hub init` — 選ばれた内容を、すべて明示した引数で受け取り、roster を書く

### 4.2 `hc-hub detect`

- 既知のエージェントの一覧（§4.4）にある実行ファイルの名前を、使い捨ての hc 端末の中の `sh -c` で、名前ごとに `command -v` を呼んで調べる（§3 のとおり、1 回の `command -v` に複数の名前を渡さない）
  - 端末は `hc run --json --bg --no-parent` で起こす。`--rm` は付けない
  - `hc wait` で終わるのを待ち、`hc read` で出力を読む。読み終えたら `hc rm` で消す
  - `which` ではなく `command -v` を使う。`which` は最小構成の環境に無いことがある
  - 見つからないものがあるとき、`command -v` は 0 以外で終わる。これは失敗ではなく、「見つからないものがある」という結果として扱う
- 同じ名前を、ユーザーの対話シェル（`$SHELL -ic`）でも調べる
  - `SHELL` が無ければ、エラーで止まる
  - 対応するのは `-ic` と `command -v` が通る sh 系のシェル（sh・bash・zsh・dash・ksh）。それ以外（fish・csh など）はエラーで止まる
  - 既存の `HC_TIMEOUT_SECONDS` と同じ時間で打ち切り、打ち切ったらエラーで止まる。対話シェルの結果を使わずに判定を続けることはしない
  - シェルの初期化ファイルが何か出力しても混ざらないよう、出力は絶対パスの行だけを拾う
- エージェントごとに、次のどれかを返す
  - `available`: hc の端末の中で見つかった
  - `shell_only`: 対話シェルでは見つかるが、hc の端末の中では見つからない。見つかったディレクトリと、直し方（core の PATH にそのディレクトリを足す）を添える
  - `missing`: どちらでも見つからない
- 出力の JSON は、エージェントごとに名前・判定・見つかったパス・起動の argv・状態の報告を実測したかどうか・注記を持つ
- hc に届かない（`HC_TERMINAL_ID` が無い、core が動いていない）ときは、エラーで止まる。対話シェルだけの結果で代用しない

### 4.3 `hc-hub init`

引数（すべて明示。既定値は持たない）:

```bash
hc-hub init --lane <レーン名> --approval auto|manual \
  --preset <preset 名>=<エージェント名> --role <preset 名>=<役割> \
  [--preset … --role …]
```

- `--preset` は 1 つ以上必須。同じ preset 名には、`--role` が 1 つずつ必要。片方だけならエラー
- 値は最初の `=` で分ける（役割の文言には `=`・空白・日本語が入ってよい）。同じ preset 名を 2 回指定したらエラー
- 同じエージェントを複数の preset に割り当ててよい（例: `impl=claude` と `reviewer=claude`）
- `<エージェント名>` は §4.4 の一覧の名前。一覧に無い名前はエラー
- `--roster` は持たない。カレントディレクトリが git の作業ツリーの最上位でなければ、エラーで止まる（ほかのサブコマンドは、カレントディレクトリの `.hc-hub.yml` を既定で読むため、最上位で実行すれば同じ場所を見る）
- 書く前に、組み立てた roster を `validate` と同じ処理で検査する（レーン名・preset 名の形、予約語 `hub` など）。通らなければ、何も書かずにエラーで止まる
- init は、選ばれたエージェントが `available` かを、§4.2 と同じ方法で確かめ直す。`available` でなければ、エラーで止まる（detect を飛ばして init を打った場合への備え）
- 書く場所は、git の作業ツリーの最上位の `.hc-hub.yml`。git の管理下でなければエラー
- `.hc-hub.yml` が既にあれば、上書きせずにエラーで止まる
- 書く内容は、`presets`・`defaults.approval`・`ledger: .hc-hub/ledger.jsonl`・`lanes.<レーン名>.agents: {}`。`command` は一覧の argv をそのまま使い、絶対パスは書かない
- `.hc-hub/` が git に無視されているかを `git check-ignore -q` で確かめる
  - 終了コード 0（無視されている）: 何もしない
  - 終了コード 1（無視されていない）: `.gitignore` に `/.hc-hub/` を追記する（ファイルが無ければ作る）。追記したことを出力で伝える
  - それ以外: エラーで止まる
- 書いたあとにも、ファイルから読み直して `validate` と同じ処理で検査する。書く前の検査に通っていれば落ちない想定だが、落ちたら書いた `.hc-hub.yml` を残したままエラーで止まる（直すのは人）
- init が書く roster には `rules` も `role_def` も入らない。どちらも roster の任意の項目で、無くても検査に通り、hub も動く。規律のファイルが要るなら、人があとから置いて roster に書き足す（SKILL.md §1 と roster.md にこの流れを書く）

### 4.4 既知のエージェントの一覧

CLI の中に持つ。新しいエージェントは、実測してからここに足す。

| 名前 | 実行ファイル | 起動の argv | 状態の報告 | 注記 |
|---|---|---|---|---|
| `claude` | `claude` | `[claude]` | 実測済み | |
| `opencode` | `opencode` | `[opencode, --prompt]` | 実測済み | 最初の依頼は `--prompt` で渡す。位置引数はディレクトリと解釈される |
| `devin` | `devin` | `[devin]` | 実測済み（2026-10-31） | 承認待ちの状態と `--permission-mode` を省いたときの挙動は未測定 |
| `codex` | `codex` | `[codex, --no-daemon]` | 未測定 | `--no-daemon` は hc のマニュアル（`hc --skill`）による |
| `copilot` | `copilot` | `[copilot]` | 未測定 | |
| `pi` | `pi` | `[pi]` | 未測定 | |

未測定のエージェントも選べる。ただし detect の出力と、hub が人に示す提案に、未測定であることを明示する。

## 5. skill の文書の変更

- **SKILL.md §1**: roster が無いときは、エラーで止まったあと、人に「init の流れで roster を作るか」を尋ねる。作るなら detect → 提案 → 人が選ぶ → init の順に進む
- **references/roster.md**: detect と init の使い方、判定の 3 つ、一覧の置き場を書く
- **references/agents.md**: 一覧と同じ内容（未測定の扱い）を揃える
- **`.hc-hub.yml.example`**: 規律のファイルの置き場を `.hc-hub/` から外す。`.hc-hub/` は台帳などの非追跡の置き場で、規律のファイルは git で管理するものだからである。置き場は `hc-hub-rules/`（設計者の判断）
- **README の hc-hub 節**: 「`.hc-hub.yml` の作り方」に init の流れを足す

## 6. 制約

- Python 3.13、PEP 723 の同梱 CLI の流儀を守る（ruff は ALL、mypy は strict）
- テストファースト。hc は既存の `tests/fake_hc.py` の流儀で偽物に差し替え、実際の hc 端末を起こさない
- フォールバックを持ち込まない。判定できないとき・前提が無いときは、エラーで止まる
- エラーは既存の CLI と同じく、標準エラーに 1 行を出して終了コード 2

## 7. 設計者の判断（確認してほしいもの）

- `--role` を preset ごとに必須にした。役割の文言に既定値を置かないため
- `.hc-hub/` が無視されていなければ、`.gitignore` に追記する（`info/exclude` ではない）。roster をチームで共有するなら、無視の設定も共有したほうがよいため
- 規律のファイルの置き場を `hc-hub-rules/` にした
- 書く場所は git の作業ツリーの最上位に限り、init は最上位で実行させる。roster は repo の直下に 1 つ、という既存の設計に揃えた
- 書く前に検査し、通らなければ何も書かない。中途半端な roster や `.gitignore` の追記を残さないため
- 対話シェルの検出が打ち切りになったら、エラーで止める。シェルの結果を使わずに判定を続けると、`shell_only` を見落として `missing` と誤って伝えるため

## 8. builder に任せること

- detect と init のコードの分け方（`hc_hub_lib/` の新しいモジュール名など）
- JSON の出力のキーの細かい名前
- 対話シェルの出力から、絶対パスの行を拾う方法の細部
