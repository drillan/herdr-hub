# context 残量と交代

worker の文脈（context）が尽きる前に、情報を失わずに入れ替える手順。hub 自身の交代は人が手で行い（自動の交代は非目標）、worker の交代は hub が判断する。

## 観測

context 残量の観測は、画面を外側から読むことを第一にする。**外側から hc read で読む**と、worker の文脈を消費しない。

```bash
hc-hub guard --op read <t>
hc read <t>
```

- **Devin CLI**: footer に使用率が常時描画される（`Context: 127k / 262k tokens (48%)`、2026-09-13 に Herdr 1 の実機で確認）。`hc read` でも同じ値が読める前提だが、hc の上では未再測定
- **Claude Code と Codex**: 常時表示が無い・読めないときの代替は、クライアント側の slash コマンド（Claude の `/context`、Codex の `/status`）を打ち込んで描画を読むこと。モデルの文脈を消費しない。読み終えたら `hc keys <t> esc` で閉じる。ターンの途中には打ち込まず、idle のときだけ使う。hc の上では未測定で、この版で確かめたエージェントは Claude Code だけ（Codex は測っていない）
- それでも取れないエージェントは**オンデマンド申告のみ**。⛔ 定期申告は禁止（往復自体が文脈を消費し、欄は捏造を招いた実績がある）。訊くときは hub が名指しし、実測値の行ごと貼らせる

## 処置の 3 択（判断は hub）

| 処置 | 向く場面 |
|---|---|
| 続行 | 残量に余裕 |
| compact | タスク途中。名前・roster・briefing が存続するので最も安い |
| 交代 | タスクの継ぎ目。hc では後任を起こして前任を止める |

「いま失って困るのは土地勘か独立性か」で選ぶ。compact は土地勘を、交代は独立性を守る。

## 交代の手順

1. **使用率 `handoff_at`（既定 0.8 = 80% 使用）で交代判定する。** roster で個別に上書きできる（範囲は 0 < x ≤ 1。[roster.md](roster.md)）
   - ⚠ 閾値は**使用率であり残量ではない**。メーターの使用率をそのまま `handoff_at` と比べる
   - ⚠ **auto-compact 済みを検出したら閾値を無視して即交代する。** 要約済みの記憶から書く handoff は二次記述で品質が劣る。検出は `hc read` で、メーターの使用率が高値から急落している、または画面に compaction の通知行がある（各エージェントの表示は未測定）
   - 閾値は handoff を書くのに十分な残量が残るうちに置く。遅らせると handoff 品質のリスクを取る（交代コストの支配項は後任の再暖機で、発火時期に依存しない）
2. **前任が生きている間に、後任を仮名 `<name>-next` で起こす**（名前は core 全体で一意なので、同名を取れない）。手順は [startup.md](startup.md)
3. **briefing の内容ブロックは前任が後任へ直接送る**（分担表は [briefing.md](briefing.md)）。前任が書くのは現在の状態・最初の一手・既知の罠、hub が書くのは宛先 guard・役割・作法・境界・進め方。hub は前任が送る内容を検査してよいが、書き換えて自分の文にしない
4. **前任の exit 後に名の整理を行う。** 正名を取るか、仮名のまま運用して台帳の記録を付け替えるか、どちらか一方は必ず行う。hc には起動後に名前を変える操作が見当たらない（確証はない）ので、通常は仮名のまま運用する。`hc-hub ledger append` で前任に `stop`、後任に仮名のまま記録する。常駐 agent の照合は名前でなく `hc-hub.role` ラベルで行うので、仮名でも roster のエントリに結びつく。前任の片付けは `hc kill` → `hc rm`

## 発火時のコストを常時の記録で減らす

交代コストの支配項は後任の context の再暖機で、発火時期に依存しない。発火時に生成する量を減らすため、次を常時行う。

- worker は進捗・判断・罠をログ file へ随時追記する（briefing の作法に含める）。置き場は repo のメインのチェックアウトの `.hc-hub/logs/<名前>.log`（非追跡）で、絶対パスを hub が briefing に書く
- handoff は「ログのパス + 差分のひとこと」で済ませる。発火時の生成コストが 0 に近づき、高い閾値でも書き切れる
- 揮発知識を随時ファイルへ逃がす。「引き継ぐものが無ければ handoff は不要」が成り立つ状態を保つ
- **試して駄目だったことを厚く残す。** 成功した手順は後任も発見するが、死に筋は書かないと同じ場所で同じ時間を燃やす

## 恒久性クラス（何が生き残るか）

handoff で「どこに書けば届くか」を決めるため、情報の置き場を生存期間で分ける。

| クラス | 例 | 生存期間 |
|---|---|---|
| 恒久（hosted） | issue tracker、repo の追跡ファイル、PR 本文 | セッション・マシンを跨いで残る。裁定・決定の置き場 |
| machine-local | `.hc-hub/` 配下のログ・台帳（非追跡）、shell 履歴 | そのマシン上では残るが、clone・別環境では消える。補助ログの置き場 |
| 揮発 | エージェントの文脈、画面の表示（`hc read` の範囲） | compact / exit で消える。ここにだけある知識は恒久か machine-local へ逃がす |

⛔ **裁定・決定を揮発や machine-local のままにしない。** 届くべき相手が読める恒久層へ置く（裁定は正典か tracker へ、逐語と裁定日で）。

**共有メモリ（複数の agent が読む置き場）の writer は hub 単独にする。** worker が各自で共有置き場を更新すると、writer が分散して更新の衝突や陳腐化の検出が効かなくなる。worker は自分のログを書き、共有置き場への転記は hub が行う。

## hub 自身の交代

hub 自身の交代は人が手で行う。前任が引き継ぎを書いてから終了し、そのあとで後任が起動する。「1 レーンに hub は 1 人」の検査（[lanes.md](lanes.md)）に例外は設けないので、前任が live のうちは後任の `hc-hub start` が失敗する。

**交代の合図**は 3 つ。①`handoff_at` 閾値（他の agent と同じ）、②auto-compact の検出、③**フェーズの変化**（大きな裁定の束が閉じた、作業の区切り）。③は閾値に依らず検討する。フェーズを跨いだまま旧 hub が残ると、新規の判断と旧裁定の経緯が混ざる。

**手順**:

1. 前任が引き継ぎ（下記）を書く。ファイルにするなら `.hc-hub/handover/<レーン>.md` に絶対パスで置く
2. 前任を終了する（人が行う）
3. 人が新しいセッションを起ち上げる。roster ファイルが新しい hub セッションの再開資材になり、後任は `hc-hub start --lane <L>` でレーン名を渡して起動する
4. 後任が hub 起動時の点検を行う（次節）
5. 後任が、引き継いだ worker の全員に、自分のアドレスを新しい返信先として `hc send` で必ず知らせる。briefing に書かれた返信先は前任のアドレスのままだからである
6. 引き継いだ worker ごとに `hc wait <t>` をバックグラウンドで並べて走らせる（次々節）

旧 hub は退く前に **3 種の引き継ぎ**を残す。①裁定の経緯（何を裁き、なぜか）、②却下した案（後任が同じ案を検討して無駄にしないため）、③worker ごとの癖（報告の精度、踏みやすい罠）。**出所ラベルを添える**（旧 hub の判断である旨）。引き継ぎは一次資料ではなく二次記述なので、出所が書かれていないと正典と同じ重みで読まれる。

**引き継ぎの形は handoff file に限らない。** 恒久層（tracker、merge 済みの文書、repo）から読めるものがほとんどなら、後任への 1 便で足りる（揮発分が 5〜7 件程度のとき、file 無しの直接の引き継ぎが 3 代連続で機能した実績がある）。揮発分が多いときだけ file を介する。

### hub 起動時の点検

起動した hub は、レーンに残っている worker を次の順で確かめる。操作の前に毎回 `hc-hub guard` を通す。

1. `hc ls --label hc-hub.lane=<L>` で候補を絞る
2. 1 件ずつ `hc get <t> --json` で `parent` と `state` を読み、親がもう生きていない worker を一覧にする（`hc ls` の各行はラベル・名前・親を返さない）
3. `hc-hub ledger list --lane <L>` と突き合わせる
4. 台帳にあるものは、引き継ぐなら `hc-hub ledger append --event adopt` で記録する。要らないものは `hc kill` → `hc rm` で片付け、`stop` を記録する。どれを引き継ぐかは hub が判断し、判断できなければ人に尋ねる
5. ラベルはあるのに台帳に無い worker は、引き継がずに人に上げる

### 引き継いだ worker の見張り

引き継いだ worker は後任の子ではないので、hc の自動の通知も `hc wait --children` も後任には届かない。引き継いだ worker ごとに `hc-hub guard --op wait <t>` の後に `hc wait <t>` をバックグラウンドで並べ、`--children any` と同じに扱う（親でない hub の `hc wait` が `blocked` で返ることは実測済み。待機の作法は [messaging.md](messaging.md)）。

### hub がいない間の限界

前任が終わってから後任が点検を終えるまでの間に worker が承認待ちになっても、誰も気づかない。hub の交代は人が行う短い作業である前提で、この空白は限界として受け入れる。自動の見回り役は置かない（hub の自動交代は非目標）。長く走らせる hub には、エージェント側の自動 compact の設定で交代の頻度を下げることを勧める。

## 共有可変ポインタ（latest 系）の扱い

「latest」「current」のような共有で可変なポインタは、複数の writer で壊れる（一方が更新すると他方の参照先が変わる）。handoff と briefing で file を渡すときは絶対パスと固定 SHA で渡し、latest 系ポインタの更新は 1 箇所（hub か担当 1 名）だけが行う。
