# hub の裁定の質

hub 自身の裁定が正しいことをどう担保するか。

## 🔴 観測を重複させない — 状態は 1 箇所が測り、判定は独立に取り直す

**すべての重複が無駄ではない。** 分けるのは**測る対象**である。

| 種別 | 例 | 扱い |
|---|---|---|
| **状態**（誰が測っても同じ値になり、既に観測者がいる） | テストの緑/赤・失敗件数・CI の結果・進捗・文脈使用率 | 🔴 **1 箇所だけが測る。** 重複は情報を増やさない |
| **判定**（主張の真偽。測り手の前提が誤りうる） | 「この定数で不変条件を満たすか」「この参照は 0 件か」 | 🟢 **独立に取り直す。** 重複が価値である |

**実測**: 独立 review 役に全量テストを回させ、**唯一の産物が stale な失敗件数**だった — 緑/赤は作者と CI が既に観測しており測り直しても情報が増えず、一方で「読んでいない file」が大量に列挙されていた — **全量実行が「読む」時間を押し出した**。
逆向きの実測: hub の算術を worker 2 者が独立に取り直し、**hub の誤りが 2 度検出された**。この重複は価値だった。

∴ **review 役に全量テストスイートの実行を求めない。** 例外は「その主張は実行しないと決まらない」ものの**名指し 1 本**のみで、何を反証しようとしたかを書かせる。

### hub 側の 2 つの誘発源

1. 🔴 **「満たされているべき不変条件」を列挙すると、受け手は全部を自分で確かめに行く。** **「読んで判定するもの」と「作者が測るもの」を分けて渡す。**
2. 🔴 **「N% で止まれ」を繰り返すと、使用率の欄が生まれる。** 欄は埋めることが目的化する（捏造の実害あり）。∴ **停止条件は hub が条件として持ち、worker には申告させない。**

## worker の主張を裁定に使う前に、1 つ質問する

> **裁定文に worker の数値・分類をそのまま引くなら、引く直前にその場で訊く。**
> 「何を測った値ですか」「変異前の値は」— 母集団と baseline を訊く。**訊く相手は worker でよい。自分で測り直す必要はない。**

**発火点は「裁定を書き始めるとき」である。** 枠組み（何を母集団として測ったか）を先に確認する — 中身の検算では気づけない。数字自体は正しく、測る対象が違っていた実例がある。

**「そのまま受け取らない」という態度では発火しない。** 枠組みの追認は「追認している」という自覚を伴わない — 相手の説明がもっともらしく、同型の欠陥を実際に見ていると、検算の必要を感じない。∴ **手続きに変換して初めて効く。**

実例: 「規約違反 86 行」→ 測っていた対象が規約と違った（実違反 1 件）/ 「この変異が一番効く」→ 既に RED で識別力ゼロ / 初報の「2 箇所」→ 実際は 3 群で、文字どおり従うと欠陥を入れるところだった。

## hub 自身の出力を疑う

**worker は hub の出力を「裁定」として受け取るので、検算のインセンティブが構造的に低い。** hub が間違えると、そのまま成果物に入る。

- **symbol 名・パス・数値を書くときは、その場で照会して出力を添える。** 添えられないものは「**未確認**」と明記して渡す。
  実例: hub が推測で書いた関数名が複数箇所へ配られ、worker が docstring へ転記した（実在しない名前だった）。
- **作用範囲（対象の集合・段）に触れる裁定は、正典の該当節を `file:行` で引いてから出す。** 実害: spec の段表が段 2 を「単一 data plane」と限定していたのに、hub が plan の入口一覧を追認して当該節を読まず、13 入口（API plane 込み）の一致を要求する判定器が実装されて live で露出した — plan も節を写しておらず、review 役にも作用範囲の一致を観点として渡していなかった。
- **裁定のために code を読むときは、worker の作業 ref を指定して読む**（同じ repo の worktree なら `git show <branch>:<path>` — push 済みの固定点を見たいときは `origin/<branch>`）。hub の checkout は worker の作業 ref と一致しない。
- **自分の裁定の周辺では、自分の検査が効かない。** ∴ 2 つ組み合わせる。
  - worker に「**私の裁定を壊しにきてください**」と明示的に招く（実際に重大な穴が出た実績あり）。
    招くときは**独立性が落ちる軸を先に申告させる**（「その材料は自分が渡したので、判定ではなく根拠の開示に留める」）。
  - **hub が「妥当」と判定したものは、その論点を最初に挙げた worker へ回して確認させる。**
    招けるのは「裁定を出した」と自覚しているときだけなので、**当事者へ回すのを既定にして自覚への依存を減らす**。
- **否定・因果・処置の行き先を含む裁定は、出す前に独立した検算役へ通す。** 発火点は「人間へ出すとき」ではなく「**裁定を出すとき**」— 宛先が人間か worker かで区別しない（worker へ渡した裁定はそのまま実装になるので、軽く扱う理由が無い）。実害: worker へ渡した裁定 2 件がこの条件に掛かっていたのに未検算で通り、「真の結論に偽の根拠が付く」ところだった。⛔ **全部の裁定を通すのではない** — 往復が増えて worker が待つ。対象はこの 3 つに絞る。
- **同じ主題で裁定が 2 巡続いて訂正されたら、検出式ではなく枠（問いの立て方）を疑う。** 実測: 同じ主題の裁定の誤り 3 件はすべて検出式の枠の中にあり、枠を出したのは review 3 巡目と「問いを 1 段上げる」検算だった。

🔴 **「疑ってよい」と言うだけでは、受け手は疑わない。**
worker の逐語: 「指示を疑ってよいと言うだけでは、受け手は疑いません — **訂正が実際に通る**のを見て初めて、検算に意味があると分かります」。
∴ **招待は宣言ではなく実績で成立する。** 最初の 1〜2 件で hub が防衛的に応じると、以後その worker は覆しに来ない。
**訂正するときは「振る舞いは正しかった / 誤っていたのは帰属だけ」まで書き分ける** — 振る舞いごと否定すると、次は逆方向（推測で進む）へ振れる。
**誤った教訓は正しい対策から遠ざける**ので、原因の帰属まで裏を取ってから訂正を配る。

**独立 review 役は誤りの検出器であると同時に発生源でもある。**
review 役が持ち込んだ欠陥が成果物へ到達した実例があり、止めた主力は下流の実装側だった — **「review 役は自己修正する」ではなく「その誤りは下流で止まる」が実態**であり、下流が居なければ止まらない。
∴ **review 役を置く設計には「その出力を裏取りする経路」を明示的に置く。** 最低 2 つ — **(a) 実害の主張は hub が一次資料で 1 件ずつ読み直す (b) review 役に「読んだ file / 読んでいない file」を毎回列挙させる**（実測で (b) は review 役自身の撤回を導いた）。
**「review 役を置けば上流の誤りが減る」と読むと、この経路を置かなくなる。**

## 過程の量を成果として数えない

**「止めた回数」「相手の判断を変えた回数」「指摘を潰した件数」は、いずれも「その処置が正しかったこと」を測っていない。** 測っているのは**過程の量**である（起きなかった害は観測できない／採用は hub の判断であって正しさの独立な証拠ではない）。
∴ **成果として数えるなら「下流で検証されたか」で数える。**

**「レビューが厚かった」を検証と読ませない記録を残す。** 指摘を多数潰した PR でも、実際に確かめられた範囲は限られていることがある — **厚さは検証ではない。** hub は報告と handoff を書く側なので、この警告を書くのは hub の責任である。

## 指示・裁定の作法

- 人間の発言は**逐語 + 裁定日**を添えて中継する。要約に置き換えない（worker が正典へ転記するとき、逐語でないと根拠が薄まる）。
- 🔴 **自分の過去の指示を指示語で指さない。** 「前便の手順どおり」は、指す先が正しく共有されている前提を作る。指示語は誤りを隠す — 受け手は「前に見たあれ」を探し、そこに無いものには気づけない。**手順は毎回自己完結で出すか、file と節名で名指す**（行番号・節番号は腐る）。
- ⚠ **進行中の branch を review 対象にするなら、SHA で pin し「着手時に取り直す」まで課す。** branch 名だけを渡すと、実装が進んだ分だけ review が stale な指摘を量産する（渡し方の正典は [briefing.md](briefing.md)「review 担当への差分」）。
- 🔴 **「ついでに」と書くときは、何のついでかを明示する。** 「ついでに」は相手が既に何かをする前提の語であり、前提が偽だと追加コストが丸ごと乗る。明示できないなら独立した指示として出し、コストを引き受けるか判断させる。⚠ **取り下げは届く前に実行されうる** — 指示を出した時点でコストが動き始めるので、出す前に前提を確認するしかない。
- **裁定は送る前に読み返し、同一便内の矛盾を検査する。** 書いている側には両立して見える。
- ⚠ **「最後のコメントを編集する」系の操作は共有 author の別便を掴みうる。** 複数セッションが同じ author で投稿する環境では、対象を ID で特定する操作を使う。

**worker の実装判断を裁く 4 段階**。根拠はそのまま成果物に載るので、結論だけを見ない:

1. **worker の根拠を一次資料で取り直す。** 差し戻しになるのは少数だが、取り直さないと 2 以降が空回りする。
2. **是認するときも「なぜ承認したか」を書く。** 根拠の強さがそのまま成果物に載る。
3. **結論が同じでも、根拠が弱ければ差し替えさせる。** 結論が正しくても、根拠が弱いまま通すと正典が弱くなる。
4. **過大主張を弱めさせる。**「確認していない範囲」を明示させる。

**裁定には「どこに置くか」まで書く。** 位置を指定しないと、実装者はコードの構造が示唆する場所に置く — 実例: 「安い fail-fast 検査を入れよ」に位置を書かなかった結果、必要な値が手に入る唯一の場所が高い工程の後だったため検査はそこへ落ちた。**検査は正しく発火しテストも緑になるが、費用は 1 円も減らない。**

**裁定を出す前に「処方が実害と同じ向きか」を確かめる。** 文面上は指摘に対応しているが、述べた目的を果たさない処方がある。

**裁定は、材料を出した全セッションへ戻す。** 宛先を「その裁定で動く人」だけで数えない — 材料を出した側が「自分の報告がそれを充足させたことは知らない」状態で古い前提を持ち続けた実例が複数ある。⚠ **「材料を出した側が裁定を追う」を規律にしてはいけない** — 届いていないものは追えない。**戻すのは裁定した側の義務**である。
