# messaging（送受信の作法）

通信は `hc send` に一本化する（[lanes.md](lanes.md)）。ここに書くのは hc send 共通の作法。worker から hub へ問い合わせるときの作法は [briefing.md](briefing.md) の「逆方向」に書く。

## 送信

- **非同期が既定。** 同期の待機は「送って即答が要る」照会だけに使う。普通の指示・裁定は投げたら送信側のターンを終える
- **送信前に宛先を確認する。** 宛先を取る操作の直前に、毎回これを打つ

  ```bash
  hc-hub guard --op send <t>
  ```

  宛先は名前かアドレスで指す。「宛先が実在するか」の確認だけでは足りない。実在確認を通って別人に届く（他レーンの worker、名前を再利用した別の worker など）。guard はレーンのラベルを読んで照合する。通らなければ送らずに止まり、別の宛先に切り替えて通さない（機構的な遮断ではないことは [lanes.md](lanes.md)）
- **本文中で他 agent を指すときも名前を併記する。** guard が守るのは宛先だけで、本文内の言及は守らない
- 長文はファイルに書いてパスを送る。サイズやバーストの超過で拒否されうる（Herdr 1 の運用の知見。hc での上限は本書では未測定）
- `blocked` の宛先への `hc send` は `--force` が無いと exit 9 で拒否される。拒否は「画面を読んでから答えよ」の合図で、答え方は [approvals.md](approvals.md)
- **送信が timeout などで返っても、未配送の証明ではない。** 再送する前に `hc read` で画面を読み、届いたかを確かめる（二重に届けない）。応答を読むときは hc read で応答を読む（画面を読む）。

## 返信

- worker → hub は `hc send <hub のアドレス>`。worker がこの経路を知るのは briefing だけなので、briefing に「あなたの名前」「同じレーンの他 agent」「返信は hub 宛」を必ず書く（[briefing.md](briefing.md)）
- **個別の依頼文にも返答経路（手段と宛先名）を明記する。** 「画面にだけ答えて送信を打たない」失敗形がある。依頼を出した側は、宛先が `idle`（または `done`）かつ自分に未着なら待たずに `hc read` でその画面を読む
- 承認済みの成果物・測定値は worker → worker で直送してよい（同じレーン内に限る）。**判断・裁定・新規の指摘は hub 経由を維持する**

## 待機と監視の作法

- **hub が子を待つのは `hc wait --children any`。** 1 分ごとの見回りは作らない。ターンを終えた agent は何もしないし、待機を回す agent は自分の文脈を監視に浪費する
- 🔴 **他者を `hc wait` で監視する指示を worker に出さない。** 監視する指示を出さない。待つべきものがあるときは「何を待っているか」を 1 行で hub へ投げてターンを終える。hub 自身の `hc wait --children any` だけが例外
- 終わったら報告させる指示を briefing や依頼に書く。**起こすのは受け手**であり、子が自分で報告できない状態（blocked・error・exited）は hc が親へ `<hc>` のタグで自動に通知する（`hc --skill`）。それ以外は、worker が `hc send` で hub に報告する
- 🔴 **「追います」「完了まで待ちます」を書かせない**（worker にも hub 自身にも）。代わりに書くのは「いま何を区切ったか」と「次に誰が動くか」だけ

### `hc wait --children any` の使い方

実測した性質（hc 0.1.15）:

- ターン終了で返る。worker が「バックグラウンドで実行中です」と宣言しただけでターンを終えたときも、`status: done` で返る。つまり返ったことは完了を意味しない
- 終了済み（exit）の子は待機の対象から外れる。待機を走らせていない間に終わった子は、次の待機では報告されない
- 子が 0 件になると、待たずに `"children":[]` で即座に返る
- ターン終了で `done` になった子は `state: live` のまま対象に残る。**live のまま idle の子が、次の待機で再び報告されるかは未測定。**

- `hc wait --children any` で待てるのは、`parent` が自分である子（自分が `hc run` で起こした worker）だけ。引き継いだ worker は親が前任なので対象外
- 戻り値の `reason` は、子の知らせ（`--children any` では全体が `children`、`hc wait <t>` では `status`）・`message`（自分に入力された）・`timeout`（待ち時間が尽きた。実測）を区別する。`hc wait --help` では、`--timeout` の既定は設定の `wait_timeout`、無ければ 180 秒（待ちが尽きたら「見に来た」と返る）

したがって、待機ループは次の形にする。

1. **待つ相手を決める。**
   - 自分の子が 1 件以上いるなら `hc wait --children any` を走らせる。自分の子が 0 件なら、この段は打たない（子が 0 件だと待たずに即座に返り、空回りする）
   - 引き継いだ worker（親が前任）は、worker ごとに `hc-hub guard --op wait <t>` の後に `hc wait <t>` をバックグラウンドで並べる（親でない hub の `hc wait` が `blocked` で返ることは実測済み）
2. **返った `reason` で分ける。**
   - **`reason: timeout`** → 全員の見回りをしない。待ち直すだけ（上の段 1 をもう一度）。`hc ls`・`hc get`・`hc read` による取り直しは、状態の知らせで返ったときだけ行う。バックグラウンドの `hc wait <t>` が timeout で終わったときは、同じ `hc wait <t>` を張り直す
   - **`reason: message`**（人や他レーンの hub からの入力が自分に届いた）→ その入力を読んで扱ってから、待ち直す
   - **状態の知らせ**（`reason: children` か `status`。子のターン終了・`blocked`・エラー・exit、またはバックグラウンドの `hc wait <t>` の戻り）→ 次の段 3 へ
3. **状態を取り直す。** `hc ls --label hc-hub.lane=<L>` と `hc get` で全 worker の状態を取り直す。戻り値だけで子の完了を数えない（通知は取りこぼされうる。完了済みの子は報告されない）。返ったあとは `hc read` で画面を読み、宣言だけで終わったか完了かを見分ける
4. **ループを抜ける条件は、自分の子も、引き継いだ worker も残っていないこと。** ここで数えるのは、`hc-hub.lane=<L>` を持ち `hc-hub.role` が hub でないターミナル（worker と常駐 agent。hub 自身は含めない）で、`state` が live のもの。idle のまま live の worker は数えるので、止める（`hc kill` → `hc rm`）までループは続く

**合図は「画面を読め」の合図であって、完了の証拠ではない。** 状態が `idle`・`done` であることを確かめてから `hc read` で回収する（`working` なら背景で待つ）。

hub が待機で張り付く形は、hub のターンを終えると待機プロセスが死ぬので効かない、という Herdr 1 の知見がある。`hc wait` が同じ性質かは hc では未測定のため、断定しない。ターンをまたいで待つ必要があるときは、バックグラウンドで走らせ、戻り値ではなく取り直した状態で判断する。

## 中継は情報を落とす

hub の中継は圧縮の工程であり、受け手は**来なかったもの**を観測できない。型ごとの処方:

| 型 | 処方 |
|---|---|
| 列挙の一部が落ちる | 指示に「N 件のうち M」と集合を再掲する |
| 参照だけ渡して本体が落ちる | 本文を同梱するか、「本人から直送させる」と明記する |
| 数えずに数を書く | 行ごとの内訳を書いてから合計する |
| 多義語を渡す | 状態は「生存 / 停止中 / 終了」等の限定語彙で書く |

- **送信のたびに通し番号と総通数を添えさせる**（(a)(b)(c)… +「本便まで N 通」）。未達 1 通はこれだけで検出できる
- **訂正・追補は「前便が生きているか」を 1 行目に書かせる**
- **worker に「私が渡した数値・区分は取り直せ」を毎回書く**

## 往復を減らす

- **ack を求めない。**「待機します」は決定を運ばない。次の指示まで待機が既定
- **訂正は次便に相乗りさせる。**単独で出すのは前便の結論が覆るときだけ
- **指摘は 1 便に合流させる。**指摘の源は非同期に届くので、届いた順に流すと受け手は同じ対象を何度も直す。blocker（そのまま進むと後続が無駄になるもの）だけ例外
- **照会には終了条件を始める前に書く。**巡回中に作った終了条件は gate の自己裁定。往復が伸びたら受け手の成果物ではなく**自分が渡した前提を疑う**

## 直列待ちを作らない

複数の判定が open なとき、順に処理すると後ろの待ちが構造化される。

- **裁定には「誰が・いつ着手するか」を書く。** 明示しないと、worker は黙って「直ちに差し戻す」を選ぶ。裁かれたことの返信は送ってよいと思う
- **hub が判定できるものは hub が閉じる。** 未解決点ごとに hub / reviewer / worker へ向きを付けて同時に進める
- **並行に行けるものは同時に出す。**別 agent なら条件付き待ちは直列化しない。受け手はいずれにせよ寝ている
- **idle を見たら理由を訊く。**「ターンが終わった」か「指示を落としている」かは hub に分からない。沈黙を進行と読まない

### 解錠 ping（「1 通にまとめる」の唯一の例外）

並行作業の発火材料になる最小情報（PR 番号 + head SHA、対象の固定点）だけは、本体の報告が溜まるのを待たず **1 行で先に投げてよい**。受け手はその行で独立 review・並行照会を即時に掛けられ、本体が届くまでの直列待ちが消える。⛔ 報告を溜めてから投げない。溜める行為自体が直列化である。

## 届いた事実を届いたタイミングで確認する

「あとで返ってくるはず」は返ってこないまま進み、時刻で「そのはず」と読む。返信・成果物が届いた事実の確認は、そのタイミングの行動である。届いたタイミングで確認して、`hc get` の状態と `hc read` の画面に当てる。

⚠ **待ち時間を訂正対象にするのは「その待ちで人間の時間を燃やしているとき」だけ。** worker が待っている間もタスクは動いているので、なんでも直列化すれば早いわけではない。

## go・承認は報告された版にだけ掛かる

hub が worker の成果物（plan・実装・回答）に go を出すとき、**対象の版を pin する**。go は報告された版にだけ掛かり、pin が無いと worker が別の版へ進んで go が別物へ効く。

- worker の報告には **対象の絶対パス + sha256sum の先頭 12 桁**を添えさせる
- hub の go 文には同じ値を併記する（`plan go <path> <sha256 先頭12>`）。worker は受けたら**手元の版と突合してから進む。**一致しなければ進まず報告する
- go の後に対象を書き換えたら go は失効する。再報告して取り直す

## 着地と停止

- 担当分が着地し次の割り当てが無いなら、その agent へは何も送らない（着地後は何も送らない）。「終了です」通知も送らない（待機は既定状態）
- 着地報告への返信・受領確認・評価の擦り合わせはしない
- **例外は 1 つ**: 走行中の review・照会を止める「停止」の 1 行。merge・完了を走行中の側は観測できないので、送らないと止まらない

### 「worker を終わらせる」は後始末まで

agent が exit しても、ターミナルの記録（と、`tab` 配置では tab）は残りうる。**終了の完了形**は、agent の exit ではなく後始末までとする。

1. 結果を受け取ってから、hub が止める（**結果（最終報告）を受け取ってから**）。報告の前に止めない
2. 止めるときは `hc kill → hc rm` の順に実行し、台帳に stop を記録する。いずれも直前に `hc-hub guard --op <op> <t>` を打つ

   ```bash
   hc-hub guard --op kill <t>
   hc kill <t>      # tab 配置の tab もこれで消える（実測）
   hc-hub guard --op rm <t>
   hc rm <t>        # ターミナルの記録を消す
   hc-hub ledger append --lane <L> --name <名前> --address <t> --hub "$HC_TERMINAL_ID" --event stop
   ```

3. hub が「残せ」と指示した場合は片付けない（証跡参照・交代の名付け用）。残せと指示した場合は片付けない。残した worker は台帳に stop を記録しない（まだ live のため）。残す理由は人に伝える

### 人が tab を閉じた worker

`tab` 配置の worker は、人が tab を閉じると終了する（core の keep が有効になるため。spec）。worker が終了すると pane が閉じ、最後の pane なら tab も消える。hub は、人が閉じた worker を「終了した worker」として扱う。待機から返ったとき、または取り直した状態で `state: finished` のターミナルを見つけたら（人が tab を閉じた worker が `finished` になるのは、spec 4.10 と `hc kill` の実測（tab が消え、ターミナルが `finished` で残る）からの推定で、人が閉じた場合を直接測ったものではない）、`hc-hub guard --op rm <t>` の後に `hc rm <t>` で記録を消し（`kill` は要らない）、台帳に stop を記録する。結果を受け取っていなければ、受け取っていない事実を人に伝える。
